# vivado-incremental-compile

**对应教程**：<https://geek-doc.cn/fpga/intermediate/vivado-incremental-compile.html>（随对应教程上线后生效）

比较同一 RTL 参考检查点下，局部 leaf 修改与顶层数据通路大改的完整实现、增量实现。两种修改各重复三次，器件固定为 Artix-7 `xc7a35ticsg324-1L`，时钟约束固定为 10ns；所有运行都从同一份 `baseline/postroute.dcp` 出发，不串用上一次结果。

## 复现（Windows，Vivado 2017.4）

```powershell
powershell -ExecutionPolicy Bypass -File run-matrix.ps1
```

脚本先建立基线，再依次运行 12 个对照流程。工具路径在脚本顶部，按本机安装位置修改。每趟只清理本实验目录内的文件，不终止其他 Vivado 会话。注意：启动时会替换 `work/`、`baseline/`、`results/` 和结果压缩包，其中也包括随包提供的报告及读者后来放入这些目录的文件，请先另存需要保留的内容。

- 小改：只替换 `leaf` 的异或常数，顶层不变。
- 大改：只替换顶层输入混合与四个结果的归并逻辑，`leaf` 不变。
- 完整实现：读取修改后的 RTL，重新综合、优化、布局和布线。
- 增量实现：重新综合修改后的 RTL，先在新综合检查点上执行 `opt_design`，再用 `read_checkpoint -incremental` 引入基线布线检查点作为复用参考。Vivado 2017.4 在读取增量参考后会跳过 `opt_design`，因此不能把优化放在该命令之后。

`flow.tcl` 为每趟输出 `EXPERIMENT_RESULT`，记录脚本内实际经过的秒数；增量流程另存 `reuse.rpt`，完整流程不伪造复用率。`matrix-summary.log` 保存控制台记录，`incremental-results.zip` 收集各次报告。由于实验规模较小，结果只适用于这个固定设计和软件环境，不能直接外推为大型工程的普遍加速比。

## 本次实测（2026-11-22）

| 修改 | 完整实现三次耗时（秒） | 完整实现均值（秒） | 增量实现三次耗时（秒） | 增量实现均值（秒） | 均值差 |
|---|---|---|---|---|---|
| 小改 leaf | 83.550 / 82.611 / 86.777 | 84.313 | 86.483 / 87.877 / 85.856 | 86.739 | 增量慢 2.88% |
| 大改 top | 83.766 / 85.187 / 85.370 | 84.774 | 84.446 / 85.753 / 83.999 | 84.733 | 增量快 0.05% |

三次运行的波动区间相互重叠，这个样本只能证明增量流程实际生效，不能证明它在本设计上稳定省时；建立基线布线检查点的 86.313 秒也没有摊入上述增量耗时。小改三趟的 Cells / Nets / Ports 复用率均为 23.96% / 5.29% / 100%，大改均为 47.51% / 4.60% / 100%。Matched 是匹配率，不等于 Reuse 复用率。

该 RTL 只有一级输出寄存器，没有寄存器到寄存器路径，Design Timing Summary 的 WNS 均为 NA，因此本实验不宣称时序收益。复用报告中的 WNS 是参考检查点元数据，不能当作本设计的寄存器间时序裕量。完整规范化控制台日志和 32 份 utilization/timing/reuse 报告在 `results/`；各趟都从同一基线重新开始，资源和时序报告用于核对实现确实完成。
